One row per version, not per host. The estate is an ephemeral VM fleet — a per-host table would be noise, and the Deployments page already owns the host census. Click a host count to expand, or Go to → hosts to open Deployments pre-filtered to exactly those hosts.

Why fragmentation is the headline. A Cloud Run service rolls forward; a VM never updates itself — one launched 3 days ago runs 3-day-old code for its entire life. So a fix shipped today never reaches VMs launched before it, and they keep writing pre-fix data. That is a data-correctness problem, and nothing surfaces it today.

The "Built · when" column answers "how old is this?" A SHA gets you to the commit but not to a date — so each row now shows when the artifact was made. Images carry a real build time (Artifact Registry createTime); tarballs say frozen at launch, because a VM never updates itself so its code is frozen at the moment it booted, and the exact tarball build time is unresolvable until the stamp lands. (Some GCP image dates here are deploy-derived — the exact createTime needs a fresh gcloud auth; the data itself is always there.)

The tarball rows are the argument for the stamp fix. Those four features-sports VMs launched in two cohorts 7h apart, and the tarball refreshes every 30 min — so they are probably running different code. We cannot prove it, because git_commit is "" on all 13 live VMs (measured 40/40 in a wider sample). The audit cleared a 2-line, zero-Python fix that records it going forward; until then these stay ⚪ unknown rather than guessing. Reconstructing history was evaluated and deliberately dropped — the honest ceiling was "±30 minutes, per repo", and a falsely precise number is worse than a blank.

This is the "final stage, fully" — and it's free. Cloud Run keeps every deploy as a numbered revision (192 for this one service, back to 2026-05-06) with its digest, timestamp, and deployer — the platform retains it at no cost. Revision N was live from its timestamp until N+1, so this table also answers "what was running on date X" — the original deployments-page question. The churn is real: ~40% of these deploys changed nothing (same digest), and AWS App Runner uts-deployment-api-prod is PAUSED today after two failed deploys — a failure the build feed can't see, because the build was green and the deploy is what broke.

The two clouds share no common tag key. GCP tags by short-SHA (6aad829); AWS ECR tags by version + latest and carries no git SHA at all — so "what commit is this ECR image?" is unanswerable from ECR alone and must be joined via the CodeBuild record. Version tags stopped appearing on GCP images around late June, which lines up with the router reading a version field no sender ever sends.
